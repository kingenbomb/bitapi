      不带什么
      
      省下来的都是不用维护的
    

    
能少一件就少一件 —— 少一个组件、少一条分支、少一套状态机。下面每一条都是刻意不做,代价也写在明面上。

    

      

        
没有 Redis

        
限流与巡检就在进程里,少一个要看着的服务。代价是必须单 worker 跑,这条写在部署说明里,不藏。

      

      

        
没有 Postgres

        
一个 SQLite 文件装完用户、密钥、流水、订单和定价。1 核 1G 的机器足够支撑数千注册用户。

      

      

        
没有构建步骤

        
前端是原生 JS,依赖自托管在仓里。改完刷新就是新版本,没有 node_modules,也没有装不上依赖的部署夜晚。

      

      

        
没有额度预占

        
请求结束后按实际用量一次结算,下一次由预检拦住。「预扣 / 退款 / 泄漏回收」那套最容易出错的状态机不要。

      

      

        
没有两套价

        
控制台里的在线体验和真接进去走同一条计费路,扣同一份余额、进同一张使用记录。体验价就是接进去的价。

      

      

        
没有 CDN 依赖

        
脚本、厂商图标、这页的字体全部本地解析。外网断了,页面还是完整的页面。

      

    

  

  

    

      口径
      
      出争议时按这几条复盘
    

    

      

        
双协议透传

        
/v1/chat/completions 与 /v1/messages 都在,流式与非流式、工具调用原样透传。

      

      

        
失败自动切号

        
一个模型名后面可以站一排上游账号,取号失败或上游限流就换下一个。限流不判死号,只轮换。

      

      

        
定价快照

        
每条用量日志冻结当次生效的单价与档位。之后改价,历史账单仍然可以精确复算。

      

      

        
用量三级归一

        
上游给了真实 usage 就采信;拿不到就本地估算;按次计费的记 0。每条日志标 token_source,分得开真实和估算。

      

      

        
看得到就调得通

        
模型广场的可见范围与网关白名单是同一份数据,不存在「页面上有、调用返回 403」。

      

      

        
断连也照实结算

        
客户端断开后网关继续排空上游、把 usage 合并完再结算,不给平台留漏记的口子。
